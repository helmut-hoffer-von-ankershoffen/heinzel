# Cap: local release-feature recording research

Read-only inspection on the Mac mini, 2026-11-08. No recording, upload, download, login, permission change, or live-service change was performed.

## Installed software and evidence

- `/Applications/Cap.app/Contents/Info.plist` identifies Cap 0.6.2, bundle `so.cap.desktop`, executable `Cap`, minimum macOS 12.3. The GUI executable is `/Applications/Cap.app/Contents/MacOS/Cap`.
- `/Applications/Cap.app/Contents/MacOS/cap-cli version` reports CLI 0.6.2, macOS aarch64, bundled distribution and the same desktop bundle. No `cap` executable was found on the inspected PATH or at `~/.local/bin/cap`, `/usr/local/bin/cap`, or `/opt/homebrew/bin/cap`. Use the absolute bundled CLI path; do not install a shim just for this workflow.
- The bundle declares screen capture, microphone and camera usage descriptions; its signed entitlements include audio input, microphone, camera, network client and server. These declarations do **not** establish actual macOS permission grants or prove the CLI has the same effective permission identity as the GUI.
- A desktop recordings directory exists at `~/Library/Application Support/so.cap.desktop/recordings`. Its contents were not inspected. CLI `record start --help` says its own default is `<recordingId>.cap` in the current working directory, and `--path` must point to a new, nonexistent `.cap` project. Do not rely on a default path for private material.
- Evidence is local `Info.plist`, `codesign -d --entitlements :- /Applications/Cap.app`, CLI `version`, and `--help` for the top level, `targets`, `doctor`, `record start`, `record stop`, `project validate`, `recordings`, and `export`. The help describes capabilities; it is not an observed end-to-end recording.

## Proposed local workflow

1. Prepare an isolated fictional demo fixture with no real accounts, tokens, notifications, personal information, or sensitive windows. Choose the smallest suitable window, inspect its surroundings, and ensure the visible screen and any audio sources are safe. Use a private, access-restricted directory outside all source worktrees, backups and shared/synced folders; set restrictive permissions before creating files. Confirm available disk space and retention/deletion arrangements. A `.cap` project can contain raw media, so protect it as carefully as the export.
2. In an approved recording session, use the bundled CLI's `targets windows --json` to discover the intended window ID. Listing targets can expose window titles; keep output private. Verify macOS Screen Recording permission for the actual capturing process interactively; permissions have not been checked here. Disable microphone, camera and system audio unless specifically needed and approved; do not pass `--mic`, `--camera`, or `--system-audio` for a silent capture. Verify the captured audio in the resulting file before sharing.
3. Set `CAP_CLI=/Applications/Cap.app/Contents/MacOS/cap-cli` and select a fresh absolute project path in the private directory. The documented CLI shape is `"$CAP_CLI" record start --window <window-id> --mode studio --path <new-project.cap> --duration <seconds> --json`. Alternatively `--detach` returns a recording ID and path; stop with `"$CAP_CLI" record stop --id <recording-id> --json`. Treat command output and IDs as private. Check command exit and finalization; do not assume success from a start event.
4. Run `"$CAP_CLI" project validate <project.cap> --json`, then `"$CAP_CLI" export <project.cap> --output <private-output.mp4> --json`. Validation checks metadata and expected media files, not privacy or playback quality. Watch and listen through the complete export, including edges, popups and transitions, and independently review it for disclosure before any sharing. Keep raw media and exports private under the agreed retention period; delete them through an agreed process when no longer needed.
5. Sharing is a separate decision. The CLI offers `upload` and may reuse Cap Desktop login; do not invoke it or other network/account commands as part of this local workflow. No automatic upload behavior during recording or export was tested; establish network behavior before recording any sensitive material.

## Limits and decisions

Screen/window enumeration, permission state, actual recording, audio defaults, output validity, local-only network behavior, sharing, and deletion were not tested. `doctor` and `selftest` were not run because their effects and possible prompts were not established. Decide the fictional fixture and target window, private storage/retention, audio requirement, independent reviewer, and whether any later publication is authorized before running the workflow. An export should never be treated as safe solely because the project validates.
