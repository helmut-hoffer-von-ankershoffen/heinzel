# Public installer acceptance

Installs what is actually published, with the literal public commands, in private homes and with no credentials, and
writes `result.json`. CI runs it as `.github/workflows/acceptance.yml` on hosted macOS and Linux runners; the file
uploaded as the artifact `acceptance-result-<OS>` is the receipt a promotion to stable reads. It publishes nothing.

```sh
python3 -I run_acceptance.py --expect-version 0.9.9 --expect-app-version 0.9.9
python3 -I run_acceptance.py --expect-version 0.9.9 --expect-app-version 0.9.9 --case 3   # one case; repeatable
```

`--expect-version published` (and `--expect-app-version published`) takes whatever is published now. That is a dry run:
the receipt records `expectation_supplied: false`, and a promotion must not accept it.

Exit: 0 for ACCEPTED, ACCEPTED_EXCEPT_UNPROVABLE, PARTIAL_PASS and the CANDIDATE_ACCEPTED* verdicts; 1 for REJECTED,
CANDIDATE_REJECTED and anything else unknown; 2 PREFLIGHT_FAILED; 3 REFUSED. A case can also end SKIPPED (nothing to
run in this configuration) or UNPROVABLE (the evidence cannot be produced here; the reason is the result). Neither fails
a run, and neither is a pass. Result: `<root>/result.json`, under a fresh `hz-acceptance-*` directory (mode 0700) in
`--root-parent` (default: `/private/tmp` on macOS, else `$RUNNER_TEMP` or the system temp directory). Roots are kept for
inspection and never reused. Each full case downloads and installs about 300 MB.

| Case | What it does |
| --- | --- |
| 1 `fresh_curl` | Literal `curl … \| sh` with uv verifiably absent from the private PATH |
| 2 `fresh_uvx` | Literal `uvx heinzel@latest` |
| 3 `retained_stopped_unit` | Fresh install; trusted unit generated by the installed SDK with intercepted registration; read-only quiescence accepts, malformed bytes deny, restored accepts; `uv tool uninstall`; malformed unit refused by the public command; literal reinstall; retained files byte-identical. Linux: the unit steps are UNPROVABLE (no user manager on a hosted runner) |
| 4 `versionless_reinstall` | Fresh install, uninstall, literal reinstall, config preserved |
| 5 `reported_error_sequence` | The reported commands in order; all run even after a failure |
| 6 `update_from_previous_app` | The previous published app installed by its explicit profile, then a user's state: an extra plugin, a disabled default, configuration. Then `hz system update` once a newer release is published, else `hz system update --source <candidate wheel>`. Core bytes identical to the target wheel, managed interpreter, configuration, inventory and choices kept, the updated app serves the target's identity and frontend, offline continuity, a second update is a no-op |
| 7 `plugin_cli_lifecycle` | Preview installs nothing; add `heinzel-example`; pin `heinzel-clock==0.9.2` then re-add to replace it with 0.9.3; disable and enable a default; remove. Inventory, receipt, history and startup checkpoint after each |
| 8 `plugin_ui_lifecycle` | A real headless Chrome (private profile, DevTools over a loopback socket, real mouse and key events): Profile menu, Settings, Plugins; add `heinzel-example` with the preview, the two-step Restart and apply; replace Clock 0.9.2 then 0.9.3 from the page; remove the example. The CLI is cross-checked after each change |
| 9 `uninstall_reinstall_retention` | Extra plugin, disabled default and configuration; `uv tool uninstall`; configuration and history retained; reinstall keeps the disabled choice; then the user wipes config, data and state and a reinstall is a fresh install |
| 10 `update_with_stopped_unit` | An installed but stopped daemon unit (registration simulated, as in case 3) while the user updates; the unit and its markers must be byte-identical afterwards and not loaded. Linux: UNPROVABLE |
| 11 `active_daemon_update` | Always UNPROVABLE. Records from the shipped Core that the daemon label and unit names are fixed constants, and what would be required |
| 12 `private_plugin` | Always UNPROVABLE: a plugin from a private repository needs a sign-in and this harness holds no credentials |
| 13 `default_is_stable` | The default never selects edge: the latest-app designation and its profile are final versions; literal `uvx heinzel@latest` and the curl installer each install a final Core (`X.Y.Z`, never a dev, pre, post or local version) with a final receipt and profile |

Every app start verifies: installed files byte-identical to accepted wheels, receipt, cached wheels, managed Python
inside the case, pending state, authenticated and unauthenticated HTTP on a reserved ephemeral port, plugin inventory
active and matching the profile, served assets byte-identical to the wheel, `hz` version, startup checkpoint, and daemon,
sharing and playback not enabled. Every phase's output is scanned for the generic app-profile error, "not proven
quiescent" and HTTP 403. "Not proven quiescent" is allowed only in the malformed-unit control.

Preflight runs before any case and executes nothing: PyPI latest and its wheel digest, the governed latest app tag,
`standard.json`, every release asset's hash, Core wheel equal on both sides, live `install.sh` equal to the release
tag. If main moved past the tag, pass `--accept-install-sh-sha256` after reviewing it. `--accept-wheel-sha256` and
`--accept-profile-sha256` bind independently accepted identities.

## Candidates and verdicts

A candidate is never a pass of the public path, and its verdict says so.

- `--candidate-wheel-url`, `--candidate-wheel-sha256` and `--candidate-profile-url` test a held final release before it
  is on PyPI: the wheel on this project's release page (its sha256 must match), and the app release's `standard.json`
  that selects it. All three go together, with explicit `--expect-version` and `--expect-app-version`. Every profile
  artifact is downloaded and hashed first; PyPI is not consulted. The app then starts from the release wheel with the
  profile as `HZ_APP_PROFILE`. Cases 1, 5 and 13 (the literal public commands) are SKIPPED. Verdicts:
  `CANDIDATE_ACCEPTED`, `CANDIDATE_ACCEPTED_EXCEPT_UNPROVABLE` (the usual outcome), `CANDIDATE_PARTIAL`,
  `CANDIDATE_REJECTED`; `result.json` carries `"mode": "candidate_release"` and `"public_path_proof": false`.
- `--candidate-wheel` (a locally built wheel), `--bootstrap` other than `literal`, and `--diagnostic-explicit-profile`
  make the verdict NOT_ACCEPTANCE_DIAGNOSTIC. `--bootstrap`: `literal` (the public command), `explicit` (published app
  by `HZ_APP_PROFILE`), `candidate-launcher` (the candidate as launcher over the governed latest app), `candidate-app`
  (a local profile with the candidate as Core and the published plugins). Never use these as evidence for the public
  path.

## Linux and hosted runners

Nothing refuses merely because it runs in CI. The service-manager checks are read only: on macOS `launchctl
managername`, `manageruid` and `list` (a registered label or a non-Aqua session makes the case REFUSE); on Linux
`systemctl --user list-unit-files` for the daemon's units, recorded as not applicable when the host has no systemd user
manager. Chrome starts without its sandbox only with `--chrome-no-sandbox true`, which the workflow sets on Linux
runners (disposable VMs).

## Isolation

Private HOME, tool, bin, Python, uv cache, config, data, state, log and unit directories per case; environment built
from nothing but LANG, LC_ALL and TERM; no credentials. PATH spies stand in for `launchctl` and `systemctl`; the run
records the listener on 8737, the real tool receipt, shim and daemon units before and after, and never contacts port
8737. `result.json` lists what is real and what is simulated under `limits`. Do not claim anything outside it.

## Vendored files

`vendor/guardian.py` and `vendor/artifact_provenance.py` are unmodified reviewed copies; their hashes are checked before
loading. This directory is excluded from ruff (`pyproject.toml`) because the hash pins forbid reformatting them, and the
harness is a self-contained, stdlib-only program that runs under `python3 -I`; `tests/unit/acceptance_test.py` covers its
verdict logic.
