# 0126: Calendar reminder scheduling (proposed)

Status: proposed; implementation is incomplete.

Calendar reminders need a deadline-aware scheduler independent of the daemon's configurable wall-clock tick. A five-minute tick is not a five-minute warning: an event may start between ticks, the machine may sleep, and Linux intentionally delays a timer. The hourly notification watcher is unsuitable too. A scheduler must discover the next boundary, wake at its five-minute offset, and refresh the bound provider before publishing. It must replan when events change and handle provider failures without inventing an empty calendar. A resumed machine must not issue an alert after its boundary. Delivery remains subject to quiet hours, notification consent and operating-system availability.

Enabling unattended calendar reads needs explicit user consent. No background read or new persistent process is enabled by this proposal. The implementation must specify installation, restart, sleep, shutdown and user-scope configuration on each supported platform, and bound provider reads and retries. Neither an open web tab nor changing the daemon interval establishes that lifecycle.

Each selected occurrence is identified by its provider, occurrence ID, actual start and end instants, and boundary kind. Store replay evidence durably and atomically with the notice. Version changes must withdraw old pending notices; unavailable or untrusted provider results fail closed. Expiry is exclusive at the meeting boundary, including for notices held by quiet hours or rate limits. A delivery claim must revalidate the current provider state, or use another design that proves a move or cancellation between the last read and the claim cannot produce a stale popup. A local withdrawal after a popup is claimed cannot retract it. Multiple processes must coordinate the validation and claim without exposing event details or holding a store lock across a provider network call.

The generic notice expiry and withdrawal primitives and the pure boundary planner on this branch are groundwork, not an operational scheduler. Provider identity, consent, bounded persistent scheduling, delivery-time validation and complete lifecycle tests are still required. The planner's keys must incorporate provider identity before integration. Durable replay receipts need a bounded, crash-safe retention strategy; deleting them while a boundary can recur permits duplicates. Existing callers and notice behavior must remain compatible.
