# 0108: Record owned installation continuity after verified changes

## Context and Problem Statement

Core and plugins release independently. An initial application composition cannot describe every later authorized
update or removal, so comparing every launch only with that composition can undo valid changes. Inspection must not
start the managed interpreter or import its plugins before deciding which installation to launch. Software changes
also need to preserve the daemon's existing off or paused state and distinguish reload requests from observed code.

## Considered Options

- **Record local installation continuity after verified mutations** (chosen).
- Reapply the original composition on every mismatch: can downgrade independently updated packages or restore removals.
- Inspect installed names by starting the target interpreter: startup hooks can run before inspection finishes.
- Treat a service-manager success as proof of new code: does not establish which version or contributions ran.

## Decision Outcome

Chosen option: **record local installation continuity after verified mutations**, because an offline launch should
respect the person's current installation without inventing publisher trust or execution permissions.

- A public kernel helper inspects an existing genuine, owned uv tool prefix without executing it. A bounded,
  deterministic fingerprint covers its receipt, installed package content and startup files. Generated bytecode
  and the continuity record itself are excluded; unsafe paths or an incomplete observation fail closed.
- The record is bound to the verified prefix and written atomically as a private regular file. Reading or checking
  it never creates or refreshes it. A missing or changed record is not silently adopted.
- A caller may refresh the record only after its explicitly authorized installation, update or plugin mutation
  has passed source, version and post-install checks. Failed or uncertain changes cannot create a successful record.
  It captures the candidate fingerprint after mutation and before those independent checks, then supplies that exact
  digest to the required `expected` parameter; recording refuses a different observed generation.
  Rollback may restore old evidence only when the current installation actually matches it.
- This is local continuity evidence. It is not publisher attestation, a Python sandbox, a human approval, or a
  provider/model/schedule grant. An actor controlling the same user's files can replace both state and evidence.
- Initial verified composition installation can seed the record. Legacy exact composition inspection may remain
  supported without writing one; unverifiable later state needs explicit inspection, never automatic downgrade.
- Daemon handover uses the state observed before a package mutation. An uninstalled, unloaded or paused daemon
  stays off or paused. An existing active service can reload, but only a fresh manager-bound execution receipt can
  establish the code and contributions that actually ran; service-manager acceptance alone remains pending evidence.

### Consequences

- Good: independent updates and removals survive offline relaunch, while inspection remains separate from execution.
- Bad: continuity must be maintained by every successful supported mutation, and damaged or externally changed
  installations can require explicit repair. Bounded fingerprinting adds startup work.

### Confirmation

The kernel helper's temporary-file tests cover deterministic observations, receipt and entrypoint validation, unsafe
paths and records, missing or changed evidence, bytecode exclusion, and inspection without starting installed code.
External Python links are bound to their resolved executable bytes; this does not cover the external interpreter's
standard library or shared libraries. Tool files and directories must be owned by the current user and not writable
by other users; the selected external executable and its parent directories may also be root-owned, with root-owned
sticky directories permitted. Successful recording rechecks the original authority and current evidence after the
atomic write. A durable pending marker makes checks fail closed after an interrupted or uncertain write until explicit
repair or a newly verified reinstall; it is never automatically adopted. Its successful removal is the commit point,
not a permission grant. A client that loses the acknowledgement cannot infer whether the commit occurred. Cooperating
writers are serialized. A concurrent change can still occur after any check, and same-user control is outside this
guarantee. Ordinary receipt queries accept canonical filesystem aliases, while continuity requires a physical prefix.
Mutation hooks, uncertain changes, independent updates and daemon off-state preservation still need their own tests
before integration. Installed-artifact UI and daemon tests remain release gates.
