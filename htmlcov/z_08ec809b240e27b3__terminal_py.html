1"""The web head's terminal: the user's login shell in a pseudo-terminal, over a WebSocket at `/api/terminal`. 

2 

3A browser can't put headers on a WebSocket, so the session token arrives as the first message, `{"token": ...}`, 

4within a few seconds, and is compared in constant time; before that the connection must pass the same checks as 

5every API request (a loopback Host on our port, our own Origin, no cross-site `Sec-Fetch-Site`). A browser always 

6sends an Origin with a WebSocket, so one without it is refused too. After that, binary frames are keystrokes and 

7text frames are JSON control messages, `{"resize": [cols, rows]}`; the shell's output comes back as binary frames. 

8Both directions are bounded: a shell that prints faster than the browser reads is paused by the pseudo-terminal, 

9and a browser that types faster than the shell reads stops being read. Closing the socket hangs up the shell's 

10whole process group (ADR 0048). When `hz ui` stops, each terminal hangs up its shell the same way and closes its 

11socket with "going away" and a reason the app shows (`Stopping`). 

12 

13POSIX only: on Windows the socket closes with a reason the app shows. 

14"""
